# JD 市场扫描（招聘网站 → 标准文档）

把 BOSS 直聘、智联招聘、猎聘上的公开岗位描述，脱敏汇总为 `docs/04-standard/` 下的市场扫描 Markdown。**产出的是「企业要什么人」的上游依据**，不是某家公司的正式 JD，也不是简历合格线正文。

开始前先读 [employ-guard-new-session](../employ-guard-new-session/SKILL.md) 与 `.cursor/rules/employ-guard-ai.mdc`。

## 何时用本 Skill

| 场景 | 动作 |
| ---- | ---- |
| 刷新已有学科扫描（如大模型） | 更新对应 `00N_jd-market-scan_*.md`，升高版本号，写修订记录 |
| 新增学科 / 就业方向 | 新文件 + 与已有扫描的**差异化对照**节；更新 `04-standard/README.md` 与看板 |
| 扫描完成后改简历标准 | 另开任务对齐 `003` / `004`；本 Skill 只负责 JD 扫描文档 |

## 硬约束（不可违反）

- **公开仓**：文档与提交不写维护者真名、机构名、对外品牌名；样本台账只写「岗位方向 + 渠道 + 能力标签」。
- **不整段照抄**招聘网站原文；只归纳能力词与频次档。
- **不把课评标准**混入 JD 扫描。
- **文风**：完整句子；中英文（及中文与数字）之间保留空格；禁用规则里的「体检、助手、流水线」等说法。
- 维护者未说「提交 / commit」前 **不 commit / push**。
- 改 Markdown 后执行 `npm run format` 与 `npm run lint:md`。

## 工作流清单

复制并逐项勾选：

```text
- [ ] 1. 确认扫描对象（更新哪份 00N / 是否新建 / 与哪份对照）
- [ ] 2. 定检索边界（目标岗位词、排除词、差异信号）
- [ ] 3. 三渠道检索（BOSS、智联、猎聘；详情不够则用列表页 + 相似职位）
- [ ] 4. 归类 + 频次分层（3.1 几乎必有 / 3.2 常见 / 3.3 加分）
- [ ] 5. 写样本台账（≥25 条脱敏索引，注明本轮替换范围）
- [ ] 6. 若有对照文档，写差异化表 + 对 003 的调整启示（不自动改正文）
- [ ] 7. format + lint；停住等维护者审阅 / 提交
```

## 第一步：定边界

读现有扫描（若有），明确：

1. **目标岗位关键词**（标题 + 职责里的信号词）
2. **排除边界**（避免与另一学科重复计数，见 001↔002 做法）
3. **本仓对齐面**（如大模型 A+B 类；C/D 只作水平线说明）
4. **时间窗口**（写实际检索月份，如 `2026-08～2026-09`）

**001 与 002 的分工示例**（可复用到其他学科）：

| 文档 | 收窄信号 |
| ---- | -------- |
| 001 大模型 | Python 应用算法、RAG/Agent 算法、微调、评测、vLLM |
| 002 智能应用 | Java/Spring 与 AI 并列、Spring AI/LangChain4j、全栈、Python+Java 混合 |

## 第二步：三渠道检索

### 渠道与条数

| 渠道 | 角色 | 每渠道目标 |
| ---- | ---- | ---------- |
| BOSS 直聘 | 主渠道 | ≥20 条标题 / 摘要 / 可开详情 |
| 智联招聘 | 主渠道 | ≥20 条 |
| 猎聘 | 补充核对 | ≥12 条 |

合计岗位描述片段 **≥50**（大版本刷新宜 **≥60**）。详情页登录墙 / 验证码时：**不伪造全文**；用列表页摘要、相似职位、多关键词补足，并在 §1 局限中说明。

### 检索做法

1. 用 **WebSearch** / **WebFetch** 按「渠道 + 岗位词 + RAG/Agent」组合检索；优先打开可读的详情或列表页。
2. 从「岗位职责 / 任职要求」抽取**能力词**，记录出现渠道与岗位类型（应用 / 算法 / Infra）。
3. 同一能力词在 **≥2 个渠道**重复出现，才可写入 §3.1；仅单渠道高频写 §3.2 或 §3.3。
4. 维护者本地若有收藏夹导出，可在修订记录注明「样本台账可再补」。

### 禁止

- 把薪资、公司品牌当作标准正文论据
- 用单篇博客 / 面经替代招聘站样本
- 把智能应用 Java 岗与大模型 Python 算法岗混成一份频次表

## 第三步：文档结构

新文档或重大刷新按 [template.md](template.md) 编排。现有范例：

- [001 大模型](../../../docs/04-standard/001_jd-market-scan_大模型岗位JD市场扫描.md)
- [002 智能应用开发](../../../docs/04-standard/002_jd-market-scan-intelligent-app_智能应用开发岗位JD市场扫描.md)

### 必备章节

| 节 | 内容 |
| -- | ---- |
| 元信息 | 版本、日期、状态、产品源、下一步 / 对照文档链接 |
| §1 抽样说明 | 目标岗位、渠道、时间窗口、做法、条数、脱敏、局限；§1.1 样本规模 |
| §2 岗位分类 | 类型表 + **本仓默认对齐哪几类** |
| §3 高频职责 | 3.1 / 3.2 / 3.3 三档频次（定性，非百分比） |
| §4 高频任职要求 | 维度表 +「对学员简历的含义」 |
| §5 样本台账 | 脱敏索引表 |
| §6 或对照节 | 与另一学科差异化（第二份扫描必须有） |
| 修订记录 | 版本、日期、说明 |

### 版本号

- 小改（台账补几条、措辞）：补丁，如 `v0.3.1`
- 重扫三渠道、频次结论变化：`v0.x` 升主版本，如 `v0.2` → `v0.3`
- 新建文档：`v0.1-draft`

## 第四步：频次怎么写

按 **3.1 → 3.2 → 3.3** 排列；每行是「主题 + JD 里常见说法（归纳）」。

写 §3 时对照上一轮修订记录：标出**本轮新增或加重**的能力词（如 Harness、Context Engineering、混合检索、MCP），便于维护者审阅。

§4「对学员简历的含义」只写方向性提示；**具体过线规则在 003 / 004**，不要在扫描里提前写合格线检查表。

## 第五步：多学科对照（可选）

当存在两份扫描（如 001 + 002）时，对照文档须含：

1. **差异化表**（主语言、框架、微调、集成、前端、年限结构等）
2. **重叠区写法对照**（同一能力词，两学科简历主语不同）
3. **对 003 的调整启示**（列条目即可；**不自动改 003**，避免混用合格线）

## 第六步：索引与交付

若新建文件或改序号：

- 更新 `docs/04-standard/README.md`
- 视需要更新 `docs/03-delivery/001_dev-board_开发看板.md`、`001_upstream-standards_上游标准引用.md` 中的链接（**与扫描文档同 PR 或维护者指定**）

交付时向维护者说明：

- 样本规模与局限
- 相对上一版的主要频次变化
- 是否建议同步 `003` / `004`

## 提交约定

- 维护者说「提交 001」或「提交 001、002」时，**只 stage 指定文件**，除非明确要求一并提交 README / 看板。
- Commit 信息：`docs(standard): …`，说明「为何重扫 / 新增哪一学科对照」。
