# 分支与合入

- **版本**：v0.1.1
- **日期**：2026-08-18
- **状态**：GitHub Flow；每个 PR 解决一个 Issue
- **产品源**：[产品说明](../01-product/001_prd_就业守护助手产品说明.md)
- **进度**：[开发看板](./001_dev-board_开发看板.md)

本仓采用 [GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow)：默认分支是 `main`，功能分支从 `main` 拉出，Pull Request 打回 `main`。不长期保留 `develop`。

---

## 1. 双仓关系

| 仓                 | 职责                                                         |
| ------------------ | ------------------------------------------------------------ |
| 上游私有业务文档仓 | 就业标准、方法、愿景与边界；口径的唯一业务来源               |
| 本仓（公开工程仓） | 可以运行的工具、老师用的命令、提示词版本、运行配置、报告模板 |

口径冲突时：**以上游业务文档为准**，并改回本仓摘要与日后的 `prompts/`，不要在本仓另外发明一套「好简历」。公开仓文档不得抄写维护者真名、机构名或对外品牌名。不要把课评「好课标准」用到简历与面试作答上，也不要复制平行课评仓的代码作为实现起点。

## 2. 分支

| 分支                                                              | 用途                                                       |
| ----------------------------------------------------------------- | ---------------------------------------------------------- |
| `main`                                                            | 默认分支；已审查、可继续往下做的代码                       |
| `feat/#N-短名` / `docs/#N-短名` / `chore/#N-短名` / `fix/#N-短名` | 从 `main` 拉出；**一个分支对应一个 Issue**；PR 打回 `main` |

不要直接在 `main` 上改文件。同时只推进一件正在进行的工作。

合入后删除远程功能分支，删除本地功能分支，切回 `main` 并快进。远程只保留 `main`。

---

## 3. Issue 与 PR

1. 先看 [开发看板](./001_dev-board_开发看板.md)，确认当前只做哪一件事。
2. 若还没有 GitHub Issue，先开 Issue。
3. 从 `main` 拉出以 `#N` 命名的分支。
4. **一个 PR 只关闭一个 Issue**。一个 PR 可以包含多次提交。
5. PR 目标分支为 `main`。正文必须写 `Closes #N`（填全编号，禁止留下空的 `Closes #`）。合入默认分支后，GitHub 会自动关闭该 Issue。
6. 维护者确认正文并授权后：push、开 PR；再授权合入时默认 **Squash**。
7. 合入前，PR 上的检查（当前是 Markdown 格式与 lint）必须通过。这是合入前的自动检查，不是另设一套人工关口。

### PR 检查清单

- [ ] `Closes #N` 已填全编号，且只关联这一个 Issue
- [ ] 仍落在当前里程碑与 [产品说明](../01-product/001_prd_就业守护助手产品说明.md) 范围内
- [ ] 未提交媒体、密钥、真实简历或面试录音
- [ ] 无维护者真名、无机构或对外品牌名
- [ ] 若改 `prompts/`：已用脱敏样例对比报告
- [ ] Markdown：`npm run format:check` 与 `npm run lint:md` 已通过
- [ ] 若改 Python：`uv run pytest` 已通过
- [ ] 若改用户可见行为：已更新 `docs/01-product` 或命令行说明
- [ ] 本地运行或校验命令已写在 PR 描述中

---

## 4. 提交信息

格式：`<type>(<scope>): <为什么>`。

`type` 为 `feat` / `docs` / `fix` / `chore`。主题写原因，不写「修改了哪些文件」。

改 Markdown 后必须先跑 `npm run format` 与 `npm run lint:md`。改 Python 后必须先跑 `uv run pytest`。

## 5. AI 可以 / 不可以

| 可以                                                          | 不可以                                           |
| ------------------------------------------------------------- | ------------------------------------------------ |
| 实现各个工具、提示词、文档、测试                              | 未经确认把真实学员隐私写入文档或提交             |
| 在维护者说出「提交 / 推送 / 开 PR / 合入」后执行对应 git 操作 | 把「开干 / 按建议来 / 实现 / 继续」当成提交授权  |
| 引用上游标准并注明路径                                        | 没有书面合格线就实现「判能不能投」或「查排版」   |
| 用脱敏样例调试                                                | `push --force` 到 `main`；跳过 hooks             |
| 合入后删除功能分支、切回 `main` 并快进                        | 一个 PR 混入多个 Issue 的无关改动                |
| 单独运行某一个工具                                            | 把老师用的命令做成内部步骤看不见、不能再跑某一步 |
| 引用平行仓的文档工具链做法                                    | 复制平行课评仓代码，或把课评口径用到本仓         |

## 7. 文档与代码双轨

| 变更类型              | 先更新文档？                                 |
| --------------------- | -------------------------------------------- |
| 新产品行为 / 命令参数 | 先改 `01-product`，再实现                    |
| 当前只做什么          | 先改 [开发看板](./001_dev-board_开发看板.md) |
| 技术栈替换            | 新说明 + 技术默认表                          |
| 仅重构、行为不变      | 可以不改产品文档                             |
| Issue / 里程碑调整    | 改开发看板                                   |
