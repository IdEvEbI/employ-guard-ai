- **版本**：v0.4
- **日期**：2026-09-08
- **状态**：辅导增强用书面口径；供 `review-projects` 执行，**不是**内容合格线
- **依据**：[003 简历书写标准](./003_resume-standard_简历书写标准.md) §3.3、§4（H2～H7）、C5 / C7 / C9 / S13 / S14 / S16；[001 / 002 JD 市场扫描](./README.md)
- **产品源**：[产品说明 §4.7](../01-product/001_prd_就业守护助手产品说明.md)
- **配套工具**：`employ-guard review-projects`

## 1. 文档角色

| 文档 / 工具                                            | 职责                                                         |
| ------------------------------------------------------ | ------------------------------------------------------------ |
| [004 简历合格线](./004_resume-bar_简历合格线.md)       | 整份简历「能不能投」                                         |
| [003 §4 水平线](./003_resume-standard_简历书写标准.md) | 过合格线后比较相对优劣（整份）                               |
| **本文**                                               | **按主项目**给出含金量档、难度档；辅导改项目写法与练习优先级 |
| `judge-resume`                                         | 不读本文做合格线结论                                         |
| `draft-questions`                                      | 出题；不替代本文档次                                         |

**硬边界**：

- 不打百分制；输出仅为文字档 **高 / 中 / 低**（JSON：`high` \| `mid` \| `low`）。
- **不做薪资匹配、不做报价、不做「值多少 K」**。
- 不替代「判能不能投」；审阅档次再高也不能写成「已过合格线」。
- 禁止模型另发明一套「好项目」；须对照下表语义。

## 2. 审阅对象与时间顺序

| 项       | 口径                                                                 |
| -------- | -------------------------------------------------------------------- |
| 输入     | 简历文本（通常来自 `read-resume`；结构化后优先用 `parsed` 项目列表） |
| 排序     | 按项目**结束时间**倒序（无结束则用开始时间）；近段在前               |
| 主项目数 | 识别 **1～3** 个主项目；近段宜作主打                                 |
| 角色标注 | 每个项目标明 `primary`（主）或 `secondary`（辅）；主项目宜少而深     |
| 不做     | 不评排版；不代写项目经历；不编造简历未写的技术                       |

## 3. 含金量档（G1）

回答：面试里这个项目**能扛多少追问、证据是否够厚**。语义对齐 003 的 H2、H5、H4、H6（链路、场景、评测量化、信息密度），按**单个项目**打档，禁止「沾边即高」。

| 档  | JSON   | 判定摘要                                                                                          |
| --- | ------ | ------------------------------------------------------------------------------------------------- |
| 高  | `high` | 业务场景清楚；本人职责落在链上；能串起输入 → 关键环节 → 输出 / 评测或结果；表述可追问、非堆砌名词 |
| 中  | `mid`  | 有场景或链路名词，但闭环不完整、职责偏清单，或结果弱、说明书感明显                                |
| 低  | `low`  | 几乎只有框架名 / 单点调用；或空泛自评；面试难以展开                                               |

每条须写 **一两句依据**（须能在简历找到对应表述）。

### 3.1 近段宜更高（G1-T）

期望叙事：**越靠近现在，含金量应越高**（近段宜作主打）。

| 情况                                                | 口径                                                                  |
| --------------------------------------------------- | --------------------------------------------------------------------- |
| 近段主项目含金量档 **不低于** 更早的辅 / 主项目     | 符合期望                                                              |
| 近段明显更浅、远段明显更深（如近 `low`、远 `high`） | **存疑 / 辅导建议**：调整主副、压缩旧项，或理顺时间与在职叙事         |
| 本条默认                                            | **不自动等同内容未合格**；是否升格为合格线硬伤，须另改 003/004 并确认 |

档次序：`high` > `mid` > `low`。

## 4. 难度档（D1）

回答：相对应用向学员常见交付，这个项目在简历呈现上的**技术与工程复杂度**（不是「学员个人感觉难不难」）。语义对齐 003 的 H3、H7 与 §3.3 方案深度；仍禁止「沾边即高」。

| 档  | JSON   | 判定摘要                                                                                                       |
| --- | ------ | -------------------------------------------------------------------------------------------------------------- |
| 高  | `high` | 多环节系统（如检索 + 生成 + 评测 / Agent 工具链 + 工程落地中至少两类写进职责），且能看出本人参与关键设计或权衡 |
| 中  | `mid`  | 有完整链路中的一段，或工程化 / 评测一带而过；技术面可讲但深度一般                                              |
| 低  | `low`  | 主要是调用聊天类 API、低代码拼装、或单一脚本级描述，缺少可追问的设计点                                         |

说明：难度「高」≠ 含金量「高」。例如技术很重但场景与职责写空，可出现难度中高、含金量中低。难度档**不**套用 G1-T「近段宜更高」。

---

## 5. 项目结构（对齐 003 §3.3）

每个主项目宜能看出：**背景 → 方案 / 任务与技术 → 本人职责 → 结果**（勿另立与 003 冲突的 STAR 四字标准）。缺背景、缺本人职责或缺结果 → 在审阅报告中标明，供辅导；是否并入合格线由 `judge-resume` 按 003/004 执行。

---

## 6. 叙事可信度存疑（P1～P8）

下列全部为 **存疑 / 辅导**，默认**不**自动写成内容未合格；是否升格由 003/004 与维护者确认。严重度统一：**存疑 / 辅导**。

| 码  | 主题           | 触发条件（摘要）                                                                                                           | 辅导取向                                      |
| --- | -------------- | -------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| P1  | 项目名称过泛   | 名称过短或过泛（如仅「健康管家」「管理系统」），看不出业务域 / 系统形态；宜补全为可辨识全称                                | 建议改名，便于检索与面试开场                  |
| P2  | 工作项目过短   | 归属**工作 / 实习**的项目，起止可解析且时长 **少于 2 个月**                                                                | 核对日期笔误，或说明短期轮岗 / 试点           |
| P3  | 近段角色偏离   | **近段**主项目职责 / 技术面与目标求职意向明显不符；**早期**项目可与目标方向不同，不因「早期做过别的」单独存疑              | 近段宜对齐意向；早期可保留但勿抢主打叙事      |
| P4  | 负责人通胀     | 简历可解析 **工作年限 ≤ 2 年**，且审阅范围内**每一个**项目都写「项目负责人」类抬头（对齐 003 C5 精神，本文只做分项目存疑） | 核对手头职责用词，避免全员负责人感            |
| P5  | 同公司重叠过多 | **同一公司**下项目时间轴允许**轻度**重叠（1 对重叠可接受）；若可解析的**重叠对数 ≥ 2** → 存疑                              | 理顺并行项目写法或拆清起止                    |
| P6  | 跨任职时段     | 项目起止明显落在已写明的**任职 / 实习段之外**，或同一项目硬跨两段雇主（对齐 003 S14 / C7 精神）                            | 核对归属公司与日期；课程 / 个人项目宜标明来源 |
| P7  | 落在在校期     | 项目时间明显落在**学历在读区间**内                                                                                         | **标注**宜区分课程设计 / 实习 / 个人项目      |
| P8  | 项目间空窗     | **仅在毕业 / 入职之后**的区间：工作 / 实习项目按时间排序后，相邻两段间隙 **≥ 2 个月** → 存疑；在校期项目之间的空窗不检     | 核对漏写项目、日期笔误，或说明空窗原因        |

说明：

- 日期解析失败 → **不**因无法计算而硬判 P2 / P5 / P6 / P7 / P8；可在报告写「时间不明，未做该项规则检」。
- P3 依赖求职意向或 `--job`；皆无则跳过。
- P4 的「工作年限」优先用简历自述或教育 / 工作段推算；推算不出则**不触发**。
- P8 的「窗口起点」：有任职段则取**最早入职月**，有学历段则取**最晚毕业月**；两者皆有时取**较早者**（先入职后毕业也从入职起检）；皆无则跳过。与 003 S16（工作经历段空窗）互补，本文只看**项目轴**。
- 与 G1-T 并列写入报告「存疑清单」；仍不替代 `judge-resume`。

## 7. 报告须写清

| 项       | 要求                                                                   |
| -------- | ---------------------------------------------------------------------- |
| 每项目   | 名称、时间、角色（主 / 辅）、含金量档、难度档、各自依据；相关 P\* 备注 |
| 近段规则 | 是否触发 G1-T 存疑；一两句说明                                         |
| 存疑清单 | P1～P8 与 G1-T 中已触发项（码 + 一两句）；未触发可不列                 |
| 可选改法 | 每项目 **不超过 2 条**可执行改法（辅导用，非合格线）                   |
| 整份摘要 | 一两句：哪个项目宜作为主打练习 / 投递叙事重点                          |
| 声明     | 不替代合格线；不含薪资；对事不对人；P\* 默认仅为存疑 / 辅导            |

---

## 8. 与水平线（H\*）的关系

| 本文档次    | 主要对齐的 003 水平线维度                                              |
| ----------- | ---------------------------------------------------------------------- |
| 含金量档 G1 | H2 链路、H5 场景、H4 评测、H6 密度                                     |
| 难度档 D1   | H3 工程化、H7 市场加分项、方案深度                                     |
| P1～P8      | 叙事可信与辅导；对齐 C5 / C7 / C9 / S16 等精神，**不**直接改合格线结论 |

`judge-resume` 仍可对**整份**输出 H1～H8；本文只做**分项目**辅导档，两者可并存，结论冲突时以合格线工具为准回答「能不能投」。
