## 1. 初筛关注点（约 30～60 秒）

用人方快速浏览简历时，通常确认以下五件事：

1. **岗位方向是否匹配**：是否为大模型应用或应用算法方向。
2. **是否具备可约访的项目**：是否至少有一条可追问的完整技术链路，而非仅会调用聊天类 API。
3. **证据是否可核对**：是否写清本人职责、具体技术用法及可追问的结果。
4. **履历是否成立**：工作是否与 AI 交付相关；时间线是否自洽（项目落在职内、年限可互算、空窗不过大、跳槽频率可接受）。
5. **版式是否可读**：页数与信息密度是否适中，便于继续阅读。

以下各节将上述事项落实为**可执行的写法**与**可检查的评价口径**。

## 2. 简历结构（先排信息，再求文采）

### 2.1 建议模块顺序

| 顺序 | 模块       | 学员写法                                                                                                                                      | 评价口径                                                                                                                                                                                          |
| ---- | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | 页眉       | 姓名、手机或邮箱、**岗位类表述**（如智能体开发工程师、算法工程师、大模型应用工程师）、工作年限。邮箱优先使用 163 等常规邮箱，尽量避免 QQ 邮箱 | 须能联系到本人；**首页基本信息须有岗位类表述**（不强制「应聘岗位 / 求职意向」四字）；婚姻状况、籍贯、性别等不宜占据主视觉；**不因使用 QQ 邮箱判不合格**；性别等可抽可不写，**不因缺性别判不合格** |
| 2    | 专业技能   | 按「模型与算法 / RAG / Agent / 工程与部署 / 评测与安全」分组列出，每组须能在项目中找到对应用法                                                | 技能不得脱离项目堆砌；所列关键技术须在项目经历中有体现                                                                                                                                            |
| 3    | 项目经历   | 精选 1～3 个主项目写深：背景 → 方案 → 本人职责 → 结果                                                                                         | 至少 1 个项目经得住追问；主项目深度应明显高于其余条目                                                                                                                                             |
| 4    | 工作经历   | 写清公司、岗位、起止时间，以及与 AI、数据或工程交付相关的职责                                                                                 | 时间线须自洽；非 AI 经历可保留，但不宜占据首页主要篇幅                                                                                                                                            |
| 5    | 教育与补充 | 学历、与岗位相关的证书或竞赛；自我评价控制在三至五行以内                                                                                      | 不因缺少长篇自我评价而判不合格                                                                                                                                                                    |

### 2.2 篇幅

| 要求            | 学员写法                               | 评价口径                                        |
| --------------- | -------------------------------------- | ----------------------------------------------- |
| 投递 PDF ≤ 4 页 | 正文控制在四页以内                     | 超过 4 页 → 排版未合格                          |
| 主项目宜少而深  | 优先写透一至两个项目，避免堆砌多个浅项 | 多项目等长且均较浅 → 水平偏低，存在初筛弃读风险 |

排版是否溢出、是否便于扫读、水印是否影响阅读，以页图为准，细则见 [004](./004_resume-bar_简历合格线.md) 排版部分。校区或试用类贴图水印不判排版不合格。

## 3. 内容要求

### 3.1 方向与可核对性

| 编号 | 标准               | 学员写法                                                                                                                                                                                   | 评价口径（过 / 不过）                                                                                                                                    |
| ---- | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| S1   | 首页岗位类表述可辨 | **首页基本信息**须出现岗位类表述（如「智能体开发工程师」「算法工程师」「大模型应用工程师」）。不强制「应聘岗位 / 求职意向」四字。仅靠项目经历或技能堆砌反推、首页看不出投什么岗 → **不够** | 首页基本信息无岗位类表述 → **内容未合格**；有表述但与全文主业明显拧着 → **存疑**（交老师复核投递策略）                                                   |
| S2   | 项目与职责可核对   | 项目、技术栈、本人职责须能在面试中说明清楚；指标须有口径。年龄、学历、工作年限可按就业辅导策略调整，以通过 HR 初筛、获得面试邀约；调整任一项时，相关数字须同步修改并保持互算一致           | 项目或职责明显虚构、面试无法对应 → 未合格或存疑；仅年龄、学历、年限与辅导策略一致且项目可说明 → **工具不判内容未合格**（真实性由就业老师把握，见下说明） |
| S3   | 技能须有项目支撑   | 写入技能区的框架、模型，至少在一个项目中实际使用                                                                                                                                           | 技能与项目严重脱节 → **未合格或存疑**                                                                                                                    |

说明：S1 看的是**首页能否扫到岗位名**，不是全文语义猜测。性别、籍贯等字段抽取即可，**缺省不构成 S1 硬伤**。

- **年龄、学历与就业辅导**
  - 部分岗位在 HR 初筛阶段会按年龄、学历过滤简历；若学员按真实情况填写，可能无法获得面试邀约。就业实践中，老师可按辅导策略调整简历上的年龄、学历、工作年限等，以争取面试机会。是否录用及后续沟通，由就业老师与学员在面试之后处理，**不在本文及本工具评价范围内**。

- **本文及本工具的职责边界**
  1. **项目与职责**是否能在面试中说明清楚（无法对应 → 未合格或存疑）；
  2. 简历各段数字是否**互算一致**（明显不一致 → 存疑，由老师修订写法，见 S15）。

- **无法核对**：在本文中特指项目、职责、技术用法等在面试中无法对应的情形；这是判断 AI 岗「能否投递」的主线。

### 3.2 能力证据（对齐 001 市场 JD）

投递大模型应用或应用算法岗位，简历须**同时**呈现以下三类可追问证据；缺一类即不能通过内容合格线：

| 编号 | 标准        | 学员最少须写到的程度                                                                                           | 评价口径                                            |
| ---- | ----------- | -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| S4   | 模型 / 算法 | 须能追问模型理解、微调（如 LoRA）、效果优化或**评测**（offline eval、Bad Case 闭环、Harness 等至少一种可说明） | 仅写「会使用 ChatGPT」→ 未合格                      |
| S5   | RAG         | 须能说明链路中至少两个环节，例如：解析或切分、**混合检索 / 精排**、生成、**溯源 / 拒答 / Query 改写**          | 仅写「使用过向量库」→ 未合格                        |
| S6   | Agent       | 须能说明规划、**Function Calling / MCP**、编排、记忆、人在回路、降级等至少一项，并写明**本人**具体工作         | 仅罗列框架名称 → 未合格                             |
| S7   | 业务场景    | 至少一个主项目须写清所解决的业务问题，避免纯技术名词堆砌                                                       | 全程无业务场景 → 水平偏低；若同时缺 S4～S6 → 未合格 |

### 3.3 项目写法

每个**主项目**建议按四段组织：

1. **背景**：服务对象、业务痛点。
2. **方案 / 技术栈**：采用的关键技术。
3. **职责**：用「设计 / 实现 / 优化 / 部署 / 评测」等动词描述本人工作，避免「参与」「负责推进」等空泛表述。
4. **结果**：可写业务结果、效率、指标或规模；**不强制写百分比**，但须能在面试中被追问。

| 编号 | 标准            | 学员写法                                 | 评价口径                                                                     |
| ---- | --------------- | ---------------------------------------- | ---------------------------------------------------------------------------- |
| S8   | 至少 1 个深项目 | 按上述四段完整写一个主项目               | 无可追问项目 → **未合格**                                                    |
| S9   | 职责可核实      | 每条职责须能回答「本人具体完成了哪一步」 | 仅有空泛职责 → **未合格**                                                    |
| S10  | 结果可追问      | 须有结果表述；有量化数字更佳             | 既无结果且方案极空 → 未合格；无数字但方案具体 → **可通过合格线**，水平线偏低 |
| S11  | 主项目数量      | 1～3 个深项目；其余条目从简              | 多个等长浅项目 → 水平偏低                                                    |

### 3.4 工作经历与个人项目

| 编号 | 标准                     | 学员写法                                                                                                                                                                                                                                                        | 评价口径                                                                            |
| ---- | ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| S12  | 非 AI 经历可保留         | 早期非 AI 工作可写入，但不宜占据首页主视觉                                                                                                                                                                                                                      | **不单独**因非 AI 经历判未合格；仅影响水平线                                        |
| S13  | 不宜仅依赖个人项目       | 若工作履历基本与 AI 无关，又几乎仅依靠个人项目支撑投递，应先补充工作侧 AI 产出或调整投递策略                                                                                                                                                                    | **个人项目为主且工作履历非 AI** → **内容未合格**                                    |
| S14  | 项目时间落在职内         | 项目起止时间须落在**对应公司**的在职时间段内；同一项目的时间不得跨至未列明的其他单位                                                                                                                                                                            | 项目明显跨单位或跨时间段 → **存疑**，交老师复核                                     |
| S15  | 基本信息互算一致         | 年龄、学历、工作年限三者须能互算（例如本科毕业年龄一般约 22 岁；总年限与各段在职之和大致吻合）。按就业辅导策略调整时，**须同步修改相关项**，避免 HR 初算即发现矛盾                                                                                              | 明显互算不通 → **存疑**，交老师修订；互算一致且项目可说明 → **工具不判内容未合格**  |
| S16  | 工作经历宜连续           | 各段在职时间宜首尾衔接；若有半年以上空窗，宜在简历或辅导记录中说明原因                                                                                                                                                                                          | 宣称总年限与各段之和不符、空窗明显 → **水平偏低或存疑**；**不单独**因此判内容未合格 |
| S17  | 跳槽频率宜可接受         | 允许更换工作；单段任职较短可以，但不宜呈现「每段均不足半年、两年内更换多家单位」的整体印象                                                                                                                                                                      | 多家单位任职均 ≤6 个月等 → **稳定性存疑 / 水平偏低**；**不单独**因此判内容未合格    |
| S18  | 结束时间不晚于投递日     | 投递中的简历：工作经历 / 项目经历的**结束时间不得晚于检查当日**；进行中的经历须写「至今」等，不得写成未来年月。工具以运行当日为基准做规则检查                                                                                                                   | 结束年月晚于检查当日 → **C7 存疑**（`pass` 仍可为 true）；不单独因此判内容未合格    |
| S19  | 量化与技术可信度须可辩护 | 结果数字须能在面试中说明口径；多 Agent / 大模型链路下「秒级完成整份合同审查」等与常识明显冲突的指标，应改写为可辩护数值。技术选型与规模同样须可辩护（如 ≤4B 小模型扛金融研报主生成、LangGraph+LangChain「共同做状态管理」写糊、向量库仅千级却写生产级金融 RAG） | 明显离谱或不可辩护 → **C6 存疑**（`pass` 仍可为 true）；有可追问结果即可过合格线    |

说明：S15 与 S2 一致——就业辅导可调整年龄、学历、年限以争取邀约，但**整份简历上的数字须互算一致**，否则往往在约访前即被 HR 筛除。S16、S17 主要影响稳定性判断，通常归入水平线或存疑，不纳入 AI 能力合格线（S4～S6、S13）。S18、S19 为**存疑**，不自动等同内容未合格。

### 3.5 文字表达（校对）

以下条目供 **`check-writing`** 对照；**默认不纳入「能不能投」的合格线**，只作改稿建议。细则以本文为准。

| 编号 | 标准           | 学员写法                                                                                                                                                     | 评价口径（工具输出）                                                                                     |
| ---- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| W1   | 无明显错别字   | 提交前通读；专有名词（框架、模型、公司名）与官网或文档一致                                                                                                   | 列出疑似错字 / 别字及修改建议；不误报常见技术英文名                                                      |
| W2   | 列表标点一致   | 同一段落或同一列表内：要么句末统一不用标点；要么前若干条用分号、**最后一条用句号**；不要混用                                                                 | 同一列表块内标点风格不一致 → 报出位置与建议统一方式                                                      |
| W3   | 中文标点为主   | 中文叙述句用全角标点（`，。；：`）；技术栈中的英文逗号可保留；勿在中文句里混用半角逗号、句号                                                                 | 中文语境下出现半角 `, . ; : ! ?`（邮箱、URL、版本号、纯英文技能串除外）→ 报出位置                        |
| W4   | 用语专业可核实 | 避免口语、网络梗（如「全家桶」「大礼包」）；职责用动词开头、无主语句；少用「熟悉 / 了解 / 参与 / 负责推进」；技能区避免满篇「熟练掌握 / 使用」，宜按类别分组 | 列出口语化、空泛句式、未分组技能堆砌及可执行改写方向；与 S9 一致处可合并提示，**不因此单独判内容未合格** |

说明：W2 与排版上的「行首标点」不同——W2 看抽出文本的列表句末一致性；行首标点仍由 `check-layout` 凭页图判断。

## 4. 达到合格线后的加分项（水平线）

以下**不作为**「能否投递」的硬性条件，仅在通过合格线后比较相对优劣。工具输出为 **高 / 中 / 低**（对应 004 的 H1～H8），禁止「沾边即高」。

| 编号 | 维度       | 高                                                                   | 中                                                         | 低                                       |
| ---- | ---------- | -------------------------------------------------------------------- | ---------------------------------------------------------- | ---------------------------------------- |
| H1   | 履历相关度 | 近段岗位名与目标方向一致，主业即 AI / 大模型交付                     | 岗位名偏泛，或意向与项目职称拧着（如意向算法、项目写后端） | 非 AI 经历占首页主视觉，或岗位与项目拧着 |
| H2   | 链路完整度 | 主项目能串起输入 → 关键环节 → 输出 / 评测 / 兜底，且本人职责落在链上 | 有环节名词，但串不成闭环叙事                               | 仅框架名或单点技术                       |
| H3   | 工程化     | 服务化、流式、测试、部署、降级 / 兜底中至少两类写在项目职责里        | 仅「用了 FastAPI / Docker」一带而过                        | 几乎无工程落地                           |
| H4   | 评测与量化 | 有评测方法或前后对比，数字可追问且不过分离谱                         | 有数字但缺口径 / 缺对比，或可信度一般                      | 无结果；或数字明显离谱（同时 C6 可存疑） |
| H5   | 场景深度   | 服务对象、痛点、使用入口 / 业务闭环清楚；仅技术编号清单不得给高      | 有场景名，职责仍是技术清单                                 | 纯技术名词堆砌                           |
| H6   | 信息密度   | 1～3 个深项目；主深次短；无空泛自评 / 课程堆砌                       | 深但说明书感或凑页（空泛自评、课程堆砌）                   | 多浅项或过长堆砌；写得多 ≠ 高            |
| H7   | 市场加分项 | 热点能力（LangGraph、MCP、GraphRAG 等）写进职责与结果且可追问        | 技能区有、项目里一带                                       | 仅罗列                                   |
| H8   | 履历稳定性 | 在职衔接清楚；近段写「至今」等可看出当前在职                         | 近段已结束且无「至今」；或有小空窗 / 互算略紧              | 频繁极短任；或结束时间落在未来（见 S18） |

## 5. 明确不作为合格条件的要求

以下要求常见于研究岗或 Infra 岗（001 中 C、D 类），**不得**作为应用向学员的内容合格条件：

- 不要求发表论文或科研产出（研究岗常见），也不要求大规模预训练、CUDA 算子开发、SGLang 源码级优化。
- 不要求硕士学历方可过线。
- 不要求英文简历。
- 不得仅因会使用 Dify、Coze 等低代码平台即视为满足 S4～S6；可写入简历，但不能替代算法、RAG、Agent 证据。
- **不要求** Harness、GraphRAG、MCP 单独成条方可过线；若完全缺少评测、工具或检索相关描述，仍按 S4～S6 判断。
- **不要求**简历年龄、学历与档案一致；本工具不核验真实性，也不因此判内容未合格（见 §3.1）。
