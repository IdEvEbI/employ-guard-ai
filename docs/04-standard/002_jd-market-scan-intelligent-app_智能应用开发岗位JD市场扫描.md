## 2. 岗位怎么分（读 JD 时先归类）

智能应用开发向 JD 常把「AI 能力」嵌进既有软件工程岗位，而不是单独开「算法研究」岗：

| 类型            | 典型标题关键词                                         | 企业更看什么                                            |
| --------------- | ------------------------------------------------------ | ------------------------------------------------------- |
| E. Java+AI 后端 | Java（AI / 智能体）、Java AI 智能体开发、后端 AI Agent | Spring 生态、微服务、与存量系统对接；Agent / RAG 为模块 |
| F. 双栈应用     | Python+Java、ai 应用开发（python/java）、混合架构      | 异构通信、Java 业务层 + Python AI 层分工                |
| G. 全栈 Agent   | Agent 全栈、智能应用开发、端侧智能体应用               | 前端交互 + 后端 + Agent 编排 + 交付 Demo                |
| H. 低代码运营   | Dify / 千帆 / Aily 方向 AI 应用开发                    | 工作流配置、知识库运营、快速上线                        |

**与大模型学科（001 的 A + B 类）的重叠**：E～H 类 JD 同样会写 RAG、Agent、Prompt、向量库。**差异**在于：智能应用开发 JD 更常把上述能力放在 **Java 微服务 / 全栈 / 业务系统集成** 语境里；大模型学科 JD 更常把同一能力放在 **Python AI 链路、效果评测、微调与推理** 语境里。

## 3. 高频职责（出现多、且跨渠道重复）

按「出现很频繁 → 常见 → 加分」排列。频次为定性档，不是精确百分比。

### 3.1 几乎每份智能应用向 JD 都会写

| 主题             | JD 里常见说法（归纳）                                                                |
| ---------------- | ------------------------------------------------------------------------------------ |
| 业务系统集成     | Agent / RAG 与 OA、CRM、ERP、权限、鉴权、日志、现有微服务对接                        |
| Java 后端交付    | Spring Boot / Spring Cloud、RESTful API、MySQL / Redis、高并发与稳定性               |
| RAG / Agent 落地 | 知识库问答、工具调用、工作流编排、多轮对话；常写 Dify / LangChain / LangChain4j 其一 |
| 工程化与运维     | Docker、CI/CD、监控告警、熔断限流、私有化 / 内网部署                                 |
| 全链路交付       | 需求 → 方案 → 开发 → 联调 → 上线；强调「非 Demo」「真实用户」                        |

### 3.2 常见（过半岗位）

| 主题          | JD 里常见说法                                                         |
| ------------- | --------------------------------------------------------------------- |
| Python AI 层  | FastAPI / Flask 封装模型能力；与 Java 通过 REST / gRPC / MQ 通信      |
| 前端或全栈    | React / Vue / TypeScript；AI 对话界面、管理后台、可视化编排           |
| AI Coding     | Cursor、Copilot、通义灵码、Trae 等；要求会用 AI 辅助写代码、写 Prompt |
| Prompt / Tool | Function Calling、MCP、结构化输出、上下文管理                         |
| 向量与检索    | Milvus / PGVector / ES；文档解析与入库；混合检索                      |
| 安全与合规    | 脱敏、内容审核、权限分级、操作留痕                                    |

### 3.3 加分或资深向

| 主题              | JD 里常见说法                                              |
| ----------------- | ---------------------------------------------------------- |
| Spring AI 生态    | Spring AI Alibaba、AgentScope-Java、LangChain4j 源码级定制 |
| 低代码 / 编排平台 | Dify、Coze、n8n；Harness 评测、Agent 可观测                |
| 微调              | LoRA / SFT 有加分，但**少于** 001 中应用算法岗的出现频率   |
| 推理引擎          | vLLM、Ollama 等多见于加分项，很少作 Java 岗硬门槛          |
| 多 Agent / 图谱   | Multi-Agent、GraphRAG；与 001 类似，但常让位于系统集成     |

## 6. 与大模型学科 JD 的差异化对照

两学科就业方向有重叠（RAG、Agent 都会出现），但**企业选人重心不同**。下表供调整大模型学科简历标准时对照；**不**表示某一学科「更高或更低」。

| 维度           | 大模型学科（001，A + B 类）                | 智能应用开发（本文 E～H 类）                      |
| -------------- | ------------------------------------------ | ------------------------------------------------- |
| 岗位叙事       | 大模型应用 / 应用算法 / RAG·Agent 算法     | Java+AI 后端 / 全栈 Agent / AI 应用开发           |
| 主语言         | **Python 几乎必备**                        | **Java 为主**，Python 为 AI 层或双栈第二语言      |
| AI 框架        | LangChain、LangGraph、LlamaIndex（Python） | Spring AI、LangChain4j、Dify；Python 框架为辅     |
| 微调 / 训练    | LoRA、SFT、评测、部分 RLHF 常见            | 多为加分；硬门槛相对少                            |
| 推理与部署     | vLLM、量化、吞吐延迟较常见                 | Docker/K8s、微服务稳定性更靠前                    |
| 效果与评测     | 幻觉、命中率、A/B、Bad Case 闭环           | Harness、可观测、线上监控；评测仍重要但表述偏工程 |
| 业务集成       | 场景与链路                                 | **与存量 Java 系统、权限、ERP 深度集成**          |
| 前端 / 全栈    | 多数 JD 不硬性要求                         | React / Vue、管理后台、对话 UI 常见               |
| AI Coding 工具 | 扫描中较少作为硬条件                       | Cursor / Copilot / 通义灵码等频繁出现             |
| 年限结构       | 「AI 相关 1～3 年」或项目深度补年限        | 「Java 2～5 年 + AI 落地 0.5～2 年」组合多        |
| 重叠区         | RAG 全链路、Agent 编排、Prompt、向量库     | 同上；**包装方式**不同（见下）                    |

### 6.1 重叠区怎么写才不会「撞车」

同一能力词，两学科简历应体现不同**主语**：

| 能力   | 大模型学科简历应突出                      | 智能应用开发简历应突出                       |
| ------ | ----------------------------------------- | -------------------------------------------- |
| RAG    | 切分策略、召回 / 重排、指标提升、Bad Case | 接入 Spring 业务、权限与审计、与知识库产品化 |
| Agent  | 规划 / 反思范式、多 Agent、评测与降级     | Tool 注册、与 Java API / MQ 对接、工作流上线 |
| Prompt | CoT / ReAct、结构化输出、版本与 eval      | 业务模板、运营可配置、与低代码平台协作       |
| 模型   | 选型、微调、推理参数                      | API 接入、网关路由、成本与限流               |
| 工程   | Python 服务、Docker、链路 trace           | Spring Cloud、数据库、缓存、高并发、CI/CD    |

## 7. 对大模型学科简历标准（003）的调整启示

以下供维护者改 [003 简历书写标准草案](./003_resume-standard-draft_简历书写标准草案.md) 时参考；**不自动改 003**，避免与智能应用开发学科标准混用。

1. **默认对齐面保持 001 的 A + B**  
   本工具当前服务大模型学科时，仍以大模型应用 / 应用算法 JD 为主依据，不必把 Java 全栈、Spring Boot 写进大模型学科的**内容合格线**。

2. **强化 Python AI 链路，而非 Java 业务栈**  
   003 应继续要求：RAG + Agent +（应用算法向）微调或评测证据；**不必**要求 Spring Cloud、MyBatis、React 作为大模型学科过关条件。

3. **标题与首屏方向词要区分**  
   大模型学科：求职方向宜写「大模型应用 / 应用算法 / RAG·Agent 算法」等，避免仅用「智能应用开发」——后者在市场上更常指向 Java+AI 全栈。

4. **重叠项目的写法要有主次**  
   若学员同时做过 Java 后端与 Python Agent，大模型学科简历应以 **Python 侧链路、效果指标、评测** 为主段；Java 集成可写，但不替代算法 / 链路深度。

5. **003 与 004 的 C3（算法 + RAG + Agent）仍适用大模型学科**  
   智能应用开发 JD 虽也写 RAG、Agent，但「算法」多体现为 Prompt / Tool / 工作流，而非微调与 offline eval。大模型学科合格线**不应**因智能应用扫描而下调算法与评测要求。

6. **若未来单独服务智能应用开发学科**  
   应另起书写标准与合格线（或 003 增开「学科分叉」章节），硬门槛会显著不同：Java 年限、Spring AI、系统集成、可选全栈。本文 **002** 即该分叉的上游依据。
