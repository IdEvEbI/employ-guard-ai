# 就业守护 · 产品说明

- **版本**：v0.2.8
- **日期**：2026-09-04
- **状态**：M0 冻结草案；本文是本仓产品范围的唯一产品源
- **读者**：维护者、协作 AI、后续实现者
- **业务口径**：上游私有文档仓；摘要见 [上游标准引用](../02-architecture/001_upstream-standards_上游标准引用.md)
- **评价口径**：判断内容能不能投，只用简历内容标准（未定稿前须维护者确认）；检查排版只看每一页的图片，不能只根据抽出来的文字假装看过版式；面试评价只看这场录音里的作答。三套检查项分开，不要混用。

> 上游愿景或就业标准变更时，先改上游，再同步本文。实现细节见 `docs/02-architecture/`；当前只做什么见 [开发看板](../03-delivery/001_dev-board_开发看板.md)。本仓为 public 仓库，本文不写维护者真名、所在机构或对外品牌名。

## 1. 问题陈述

有两件事高度依赖个别老师的精力和经验，别人很难模仿：

1. **投前看简历**：学员通常用 Word 写好，再转成 PDF 投递。老师拿到的检查对象是这份 PDF：能不能投、改哪几处。
2. **听后做复盘**：学员参加面试时，进门前开录音、离开后关录音；回校后老师带着学员一起听，找出这一场里的问题，并给出下次可改的建议。

本仓提供一组在本机运行的小工具。每个工具只做一件事，并把结果写成文件。`employ-guard` 按老师的两个日常动作，依次调用这些工具。标准与方法仍以上游文档仓为准。不在本仓另写一套「好简历」，也不把课评里的「好课标准」用到简历和面试上。

工具补的是可以重复做的检查与复盘。学习缺口仍靠教学；不敢投简历仍靠班级节奏与信任；谁先投、谁暂缓仍由老师判断。

## 2. 用户、形态与报告写法

| 项       | 说明                                                                         |
| -------- | ---------------------------------------------------------------------------- |
| 第一用户 | 维护者本人：抽查简历与录音、单独运行某一个工具、修改提示词                   |
| 后续用户 | 一名校区就业主责教师代跑（两条老师用的命令可用之后再内测）；不向全班开放自助 |
| 形态     | **本机命令行**；无账号、无门户、不接入公开绩效考核                           |
| 场景     | 线下现场培训与线上培训（具体品牌不在本仓展开）                               |
| 学科     | 可选；本期缺省为程序方向（大模型）。运行时由维护者指定                       |

报告把意见分成两栏，避免把「可以更好」写成「不能过关」：

- **合格线**：不过关、必须改。简历上是挡住投递的硬伤（因此判定不能投）；面试上是这一场必须改掉的问题。
- **水平线**：已经能过关，但可以更好。只当建议，不要拿来判「不能投」或「这场不合格」。

「判能不能投」「查排版」和「面试评价」都这样分栏，并且对事不对人。三套检查清单不要混用。

报告与产品文案还必须遵守：

1. 以建立可复用系统为导向，写出可以执行的改法，避免只堆批评。
2. 对事不对人；报告默认私密，不在班级群点名。
3. 先保证可读，再追求简短；使用完整句子；禁止电报体。
4. 公开仓脱敏：不写维护者真名、所在机构或对外品牌名。

## 3. 工具和老师怎么用

本仓只做一个 Python 包，不要拆成两个仓库。

| 是什么           | 谁在用                           | 做什么                                                                                 |
| ---------------- | -------------------------------- | -------------------------------------------------------------------------------------- |
| **工具**         | 维护者调试；老师用的命令也会调用 | 每个工具只做一件事，写出文件。失败时说明原因并给出退出码。下一步只读取上一步写出的文件 |
| **老师用的命令** | 老师日常                         | 按固定顺序调用一组工具。某一步已经有结果文件，就跳过这一步。本期老师只需记住下面两条。 |
| **入口**         | 老师与维护者                     | 都从 `employ-guard` 进入。老师运行下面两条；维护者可以单独运行某一个工具               |

以后若增加知识库、模拟面试、把现场问过的题留下来，应做成新的工具或新的老师用命令，而不是把现有的 `resume` 或 `interview` 再往里增加步骤。

本期老师只需记住两条命令：

```bash
uv run employ-guard resume <简历.pdf>
uv run employ-guard interview <录音> [--resume <简历.pdf>]
```

## 4. 各个工具

命令名在实现时写入命令行说明，本文先锁定中文职责和英文名。默认输入在 `data/input/`，输出在 `data/output/`（均已 gitignore）。每次运行按输入的相对路径建立目录。

| 工具           | 命令               | 输入                         | 输出                                | 为什么单独做成一个工具                                          |
| -------------- | ------------------ | ---------------------------- | ----------------------------------- | --------------------------------------------------------------- |
| **PDF 出图**   | `pdf-to-images`    | PDF                          | 每一页的图片                        | 排版只能看页图，不能看抽出来的字                                |
| **查排版**     | `check-layout`     | 页图 + 排版合格线            | 排版合格或未合格；合格线 / 水平线   | 和「内容能不能投」不是同一件事                                  |
| **读简历**     | `read-resume`      | PDF（扫描件可 OCR）          | 可供阅读的文本                      | 读失败不该和「能不能投」混在一次报错里                          |
| **查文字表达** | `check-writing`    | 简历文本 + 书写标准 §3.5     | 文字表达待改项清单                  | 错别字、标点、用语与「能不能投」不是同一件事                    |
| **判能不能投** | `judge-resume`     | 简历文本 + 内容标准          | 合格或未合格；合格线 / 水平线；分项 | 只评内容；不要顺便出题，也不要凭文本评排版                      |
| **出练习题**   | `draft-questions`  | 简历文本；可选岗位说明       | 按主项目分组的基础题与深挖题        | `resume` 完整模式会跑；排查模式可关；和「能不能投」不是同一件事 |
| **项目审阅**   | `review-projects`  | 简历文本；可选岗位说明       | 每主项目含金量档 / 难度档与依据     | 独立工具；默认不进排查；**不含薪资**；不替代「能不能投」        |
| **转写录音**   | `transcribe`       | 现场音频（视频则先抽出音轨） | 带时间的逐字稿                      | 转写质量要单独看；已有稿子时应能跳过                            |
| **还原问答**   | `extract-qa`       | 逐字稿                       | 问了什么、大致怎么答                | 老师听录音时先要这张清单，评价可以后做                          |
| **面试评价**   | `review-interview` | 问答列表；可选同一份简历文本 | 主要问题、整体评价、不超过 3 条改法 | 用面试作答的检查项，不用简历内容标准                            |

本期只检查 **PDF**（投递用成品）。手头材料已经是 PDF，不在本仓做 Word 转 PDF。输入若不是 PDF，直接失败并说明请先转成 PDF，不要开始查排版或判能不能投。`word-to-pdf` 留到确实只剩 Word 原稿时再做成独立工具；届时转换失败仍不得判成内容不合格。

PDF 出图、读简历不依赖评价标准，文档写定之后就可以做。「判能不能投」和「查排版」必须先有书面合格线（优先写在上游；未定稿前由维护者确认一份临时合格线）。没有书面合格线，这两个评价工具不要开始做，否则模型会自己发明一套「好简历」。

### 4.1 PDF 出图

- **必须**：一份 PDF（投递用的成品）。
- **必须跑通**：按页生成图片，页序与 PDF 一致；失败时给出明确退出码。
- **输出**：`pages/` 目录下按页码命名的图片。
- **不做**：在这一步评价排版好坏。

### 4.2 查排版

- **必须**：PDF 出图得到的页图。
- **必须**：书面排版合格线（页数、边距、对齐、文字是否溢出、是否过密或过疏等；未定稿前由维护者确认）。
- **必须跑通**：只根据页图检查排版；合格线与水平线分开写。不得只根据抽出来的文字假装看过版式。
- **输出**：`{stem}.layout.md` / `{stem}.layout.json`。
- **不做**：评价项目写得对不对（交给「判能不能投」）。用能看图的模型还是用规则，实现时另写技术说明并锁定。

### 4.3 读简历

- **必须**：一份 PDF。纯文本仅作备用。不以 Markdown 为默认输入。不是 PDF 则不要调用本工具。
- **必须跑通**：抽出可供后续工具阅读的文本；失败时给出明确退出码。文字层为空时（常见于扫描件）可在本工具内用本机 OCR 兜底；OCR 失败仍算读失败，**不得**写成内容不能投。
- **输出**：`{stem}.resume.md` / `{stem}.resume.json`（可标明是否经 OCR）。
- 一次调用只读 **一份** 简历。
- **不做**：在这一步判断能不能投，也不在这一步评价排版。

### 4.4 查文字表达

- **必须**：读简历写出的文本（或同样内容的文本文件）。
- **必须**：书面书写标准中的文字表达条文（[003 §3.5](../04-standard/003_resume-standard_简历书写标准.md)）。
- **必须跑通**：对照 W1～W4 列出待改项；**默认不因此判内容不能投**；有问题时退出码仍为 0。
- **输出**：`{stem}.writing.md` / `{stem}.writing.json`。
- **不做**：判能不能投；评排版；出练习题。

### 4.5 判能不能投

- **必须**：读简历写出的文本（或同样内容的文本文件）。
- **必须**：书面内容标准（简历该写什么、项目怎么写才算能投）。优先写在上游就业标准里；未定稿前由维护者确认一份临时合格线，写入提示词之前须书面确认。没有这份标准，本工具不要开始做。
- **可选**：学科（缺省见第 2 节）；目标岗位说明。没有岗位说明时，报告须标明「通用技术面，不是针对某一企业」。
- **可选、有则更好**：本学科讲义或项目要点摘录。有则检查项目描述是否与课上交付对得上、有没有把不会的写成会的；没有也不强求。
- **必须跑通**：
  1. 只用内容标准。不得凭空发明另一套「好简历」，不得用面试里的问题来判简历，也不得凭文字给排版结论。
  2. 先给 **合格或未合格**（要回答的是内容上能不能投），再给分项说明。
  3. 未合格须写清主要卡在内容、结构、逻辑还是项目描述。意见要可以执行，避免只写「再优化项目经历」。
  4. 合格线与水平线分开写。
- **输出**：`{stem}.judge.md` / `{stem}.judge.json`。不打百分制分数，不用分数替代老师的分批决策。
- **不做**：代写项目经历；生成可直接投递的简历成品；出练习题；评价排版。

### 4.6 出练习题（按项目）

- **必须**：读简历写出的文本（或同样内容的文本文件）。
- **可选**：目标岗位说明。没有岗位说明时，须标明「通用技术面，不是某家公司的真题」。
- **必须跑通**：识别简历主项目；每个主项目约 5 道基础题（含考察点与可能追问）+ 约 3 道深挖题；标明推测、供练习。
- **输出**：`{stem}.questions.md` / `{stem}.questions.json`（内容按主项目分组）。
- **编排**：`resume` **完整模式**调用本工具；`--triage` / `--no-questions` 可关掉；亦可单独再跑。
- **不做**：把练习题写成企业真题；替代「判能不能投」；评排版；另写第二套扁平题文件。

### 4.7 项目审阅（含金量 / 难度档）

- **必须**：读简历写出的文本（或同样内容的文本文件）。
- **必须**：书面项目审阅口径（[005](../04-standard/005_project-review_项目审阅口径.md)）。没有这份口径，本工具不要开始做。
- **可选**：目标岗位说明。没有岗位说明时，报告须标明「通用技术面，不是针对某一企业」。
- **必须跑通**：
  1. 识别 1～3 个主项目；每个给出 **含金量档** 与 **难度档**（高 / 中 / 低）及依据。
  2. 合格线与审阅档分开：本工具**不回答**能不能投。
  3. **不做薪资匹配**。
- **输出**：`{stem}.projects.md` / `{stem}.projects.json`。
- **编排**：独立工具；默认**不**挂入 `resume` 必跑路径，也**不**进 `--triage`；可单独再跑。
- **不做**：代写项目经历；百分制；用审阅档替代合格线；评价排版。

### 4.8 转写录音

- **必须**：一段真面试现场音频；若是视频，先抽出音轨。已有转写稿则可跳过本工具。
- **必须跑通**：生成带时间信息的逐字稿。默认在本机使用 **mlx-whisper**（`large-v3-turbo`）；不使用云端语音识别。
- **输出**：`{stem}.raw.md` / `{stem}.raw.json`。
- **不做**：在这一步评价作答好坏。

### 4.9 还原问答

- **必须**：转写得到的逐字稿（或已有的逐字稿）。
- **必须跑通**：整理成问答列表：问了什么、学员大致如何作答。
- **输出**：`{stem}.qa.md` / `{stem}.qa.json`。
- **不做**：在这一步写合格线改法（交给「面试评价」）。

### 4.10 面试评价

- **必须**：还原问答得到的列表。
- **可选**：同一学员用来投递的简历文本（通常来自读简历）。未提供时，报告须标明未做简历对照。
- **必须标明**：企业与岗位能填则填；本期只写在报告开头，**不写入题库**。
- **必须跑通**：
  1. 优先看这一场卡住的地方，而不是先评口头禅。至少覆盖：有没有听清问题；项目描述是否与简历一致（若提供了简历）；会不会把不会的说成会的；有没有把课上练习讲成自己的独立经历。
  2. 给出整体评价，以及 **不超过 3 条** 下次可改的动作。
  3. 合格线与水平线分开写。不要用简历「能不能投」的内容标准来做面试评价。
- **输出**：`{stem}.review.md` / `{stem}.review.json`。
- 吐字、仪容、学员紧张程度等无法凭稿子核对的事项，不得写成合格线必须改。工具不替代老师带着学员听。

每一步另写运行记录（输入文件校验值、所用型号、提示词版本）。真实简历、录音、完整逐字稿不进 Git。

## 5. 投前看简历：`resume`

```bash
uv run employ-guard resume <简历.pdf>
uv run employ-guard resume <含PDF的目录> [--triage]
```

老师要的是：这份投递用 PDF 能不能投、版式过不过关、改哪几处，并顺便给一组练习题。目录批跑时写出本机总表，便于排查一摞，不上门户。

**调用顺序：**

1. PDF 出图，然后查排版。
2. 读简历，然后查文字表达，然后判能不能投，然后按项目出练习题。

第 1 步与第 2 步都依赖 PDF，可以先后运行，不必互相等待评价结果。某一步已经有结果文件，就跳过这一步。按项目出练习题放在读内容和判断之后，可以关掉，也可以单独再跑一次。出图或读简历失败时，不得写成内容不能投或排版不合格。输入不是 PDF 时，直接失败并说明请先转成 PDF。

一次默认检查 **一份** 简历。老师**显式指定目录**时，可对目录下一层 PDF 批跑并写出本机总表（不上门户、不在班级群点名）。不自动扫描未指定的全班目录。本期输入必须是 PDF。

## 6. 听后做复盘：`interview`

```bash
uv run employ-guard interview <录音或转写稿> [--resume <简历.pdf>]
```

本期默认场景是**真面试现场录音**：进门开、出门关；回校后老师与学员一起听。工具给出问答清单和改法，供这次复盘当提纲，不替代一起听，也不替代老师做分批。

**调用顺序：** 转写（已有稿则跳过），然后还原问答，然后做面试评价。若给了 `--resume`，须为 PDF：先读简历得到文本，再交给面试评价，用来对照项目描述。输入不是 PDF 时，直接失败并说明。听后做复盘**不运行**查排版。

若用同一条命令处理模拟面试，步骤相同，只在报告开头标明来源。本期不单独做学员自助刷题。单份报告可以列出这场问了什么，但不得对外宣传为某企业题库。

## 7. 练习题和现场问过的题

必须分开写，不要都写成「某企业真题」：

| 类型             | 从哪来                                           | 哪个工具负责                  |
| ---------------- | ------------------------------------------------ | ----------------------------- |
| **练习题**       | 根据简历按主项目推测面试可能问到什么，给学员练习 | `draft-questions`             |
| **现场问过的题** | 这段真面试录音里实际问到的                       | `extract-qa` 列出；不写入题库 |

| **知识库**     | 新工具：用大纲与讲义摘录支撑「课上是否教过」                          | 愿景；可先手工摘录进提示词   |
| **模拟面试**   | 新工具或新的老师用命令：学员按练习题录音作答，程序只评这一轮          | 愿景；前两条命令稳定后再做   |
| **真面试入库** | 新工具：标明企业与岗位，把现场问过的题留下来                          | 愿景                         |
| **企业查询**   | 新工具：按企业、岗位查询历史上出现过的题型；默认不点名具体学员        | 更晚再做；须有积累与同意规则 |

同一时期只推进一件完整的事。默认顺序：M0 文档写定 → 书面简历合格线（内容与排版，可先用临时合格线）→ 投前看简历可以演示（先做出图与抽文本，有标准后再判断内容和排版）→ 听后做复盘（转写更重，后做）。知识库及以后的能力，不作为本期必须交付。Word 转 PDF 不作为本期必须交付，遇到只剩 Word 原稿时再开。

## 9. 明确不做

- 学员全员自助门户、账号体系、班级排行榜
- 自动生成可直接投递的简历成品，或代写项目经历
- 用分数替代老师的分批决策（谁先投、谁暂缓仍由教学和班级管理判断）
- 企业面试查询、按人点名「谁去过哪家公司」（更晚的工具另议）
- 替代按日就业台账，或自动计算全班面试邀约率
- 把课评「好课标准」用到简历与面试作答上
- 把云端语音识别作为默认转写方式
- 把知识库及以后的能力做成本期必须交付
- 在 Git 中存放真实简历、录音、完整逐字稿、密钥或可识别的商业秘密
- 把本仓写成第二份组织级标准文档仓
- 复制平行课评仓代码作为实现起点
- 在课评工程仓里加入就业辅导功能（那是另一条产品线）
- 为两个日常动作各建一个 Git 仓库
- 把老师用的命令做成内部步骤看不见、不能单独再跑某一步
- 只根据抽出来的文字，假装已经检查过排版
- 没有书面合格线，就让模型自己发明一套「好简历」或「好排版」
- 把 `.docx` 当成可检查输入，或在本仓做 Word 转 PDF（遇到只剩 Word 原稿时再开独立工具）
- 在项目审阅里做薪资匹配或报价（含金量 / 难度档可以；薪资本期明确不做）

## 11. 成功标准

### 11.1 投前看简历何时算过关

对维护者选定的若干份真实投递 PDF，`resume` 能够按顺序做完出图、查排版、读文本、判能不能投、出练习题。内容结论与排版结论分开写。维护者愿意拿它抽查「投递一周零邀约」学员的简历，而不是演示一次后搁置。输入不是 PDF、出图失败或读简历失败时，不得写成「不能投」；查排版必须依据页图。

### 11.2 听后做复盘何时算过关

对若干段真面试现场录音，`interview` 能够按顺序做完转写、还原问答、面试评价。问答列表可供老师带着学员听时当提纲；评价读起来像听完录音后的复盘，而不是「表达再自信一些」；最多 3 条改法。练习题和现场问过的题不要混写成某企业真题。已有转写稿时，应能跳过转写，只跑后面两步。

就业标准未定稿前，「判能不能投」和「查排版」以维护者确认的临时合格线为准；标准成文后改对应提示词，并升高本文版本。没有书面合格线，这两个评价工具不算过关。
